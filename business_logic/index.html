Бизнес-операции

Все операции доступны только активным администраторам гостиницы (is_staff=True). Изменяющий запрос с сессией требует CSRF-токен. Токен передаётся в Authorization.

Заселение

POST /api/check-in/:

{"room": 1, "guests": [1, 2], "check_in": "2026-11-01", "planned_check_out": "2026-11-05"}

Ответ 201:

{"id": 1, "room": 1, "check_in": "2026-11-01", "planned_check_out": "2026-11-05", "actual_check_out": null, "price_per_night": "5000.00", "guests": [1, 2]}

Проверяются существование номера и гостей, непустая группа без повторов, вместимость, выезд строго позже заезда, занятость номера и пересечение проживаний каждого гостя. Тариф определяется сервером; передавать price_per_night нельзя. Создаются одна Accommodation и несколько Stay. Транзакция откатывается при ошибке. Для конкурирующих запросов сначала блокируются гости по ID, затем номер через select_for_update().

Периоды считаются полуоткрытыми: [check_in, check_out). Конец — фактический выезд, если заполнен, иначе плановый (Coalesce в ORM). Поэтому в день выезда можно заселить следующую группу. Будущие даты разрешены. NULL actual_check_out означает, что выселение ещё не оформлено, но расчёт пересечений всё равно использует плановую дату.

Выселение

POST /api/accommodations/1/check-out/:

{"actual_check_out": "2026-11-04"}

Ответ 200 имеет ту же структуру заселения с заполненным actual_check_out. Выезд может быть раньше или позже плана, но строго позже заезда. Проверяются конфликты с другими заселениями номера и гостей, повторное выселение запрещено. История и тариф сохраняются, записи не удаляются.

Сотрудники и уборка

Приём — POST /api/employees/ с ФИО и hired_on:

{"last_name": "Тестовая", "first_name": "Анна", "hired_on": "2026-01-01"}

Увольнение — POST /api/employees/1/dismiss/:

{"dismissed_on": "2026-10-21"}

При отсутствии даты берётся сегодняшний день Europe/Moscow. Увольнение не может быть раньше приёма или в будущем; состоявшееся увольнение нельзя отменить. Будущие назначения удаляются, действующие закрываются датой увольнения, прошлые сохраняются. Связанный User деактивируется. PATCH dismissed_on использует тот же сервис.

POST /api/cleaning-schedules/:

{"employee": 1, "floor": 1, "weekday": 0, "valid_from": "2026-11-01", "valid_to": null}

Дни недели: 0 — понедельник, 6 — воскресенье. Период [valid_from, valid_to), NULL означает бессрочное назначение. Нельзя назначать уволенного сотрудника, начинать до его приёма, задавать окончание не позже начала или пересекающуюся запись с теми же employee/floor/weekday. На этаж допускаются разные сотрудники.

PATCH /api/cleaning-schedules/<id>/ меняет будущее назначение непосредственно. Для уже начавшегося создаёт новую версию и закрывает старую, сохраняя историю. По умолчанию новая версия начинается сегодня. Завершённое назначение неизменно. DELETE отменяет будущее назначение либо закрывает начавшееся сегодняшней датой; завершённое удалить нельзя. Проверки и запись выполняются в транзакции с блокировками.

Django Admin

Все восемь моделей доступны для просмотра при наличии стандартного права view. Accommodation, Stay, CleaningSchedule, Room, RoomType и Employee нельзя создавать, изменять или удалять через Admin, включая суперпользователя. У Room и RoomType ограничение предотвращает обход защиты типа/этажа и вместимости, у Employee — обход увольнения и проверки дат назначений. Их изменение выполняется через API. Floor и Guest используют стандартный Admin с ограничениями модели и PROTECT. Прямой ORM и shell предназначены для доверенного разработчика и могут обходить проверки сериализаторов; универсальная защита прямых ORM-записей здесь не реализована.
